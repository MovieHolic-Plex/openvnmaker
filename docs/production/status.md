# Production authoring and native release work

The target is an open-source authoring tool that can produce independently distributed, long-form commercial visual novels. A polished bundled example alone does not meet that target. This work is **in progress**, not a production-readiness declaration.

Optional scene-scoped line and choice IDs are validated and preserved through normal editing. New projects and missing/copied entries receive IDs; legacy manuscripts remain readable. Native release comparison now matches by ID when both lists are fully identified, independently for lines and choices; partial or legacy lists keep the content/position fallback. Duplicate-caption reordering is distinguished from surviving-entry changes, and added/removed IDs are reported even at unchanged counts. Project-library writes now request IndexedDB `durability: strict`. Before sample/edition initialization, a missing quick-recovery key triggers a durable library lookup. The active project is preferred; if its pointer is gone, the most recently stored candidate is explicitly offered for review. Initial test timeout came from awaiting a crash command that cannot respond after termination; the test now observes context closure. The subsequent genuine sample-reset failure led to the storage/startup fixes above.

## Recovery from damaged quick-save manuscript — 2026-09-06

## Latest-manuscript autosave status and retry — 2026-09-06

### Portable project folders — 2026-09-06

The project library provides **폴더에 백업 / 폴더에서 가져오기** through the browser directory picker. Each backup creates a fresh child directory, copies original media one file at a time and writes `vnmaker-project.json` last as its completion manifest. Existing backups are not overwritten. The data-only manifest contains the validated manuscript and exact required file paths, byte counts and SHA-256 hashes. Gateway images are rebased to portable user asset paths. Import rejects unsupported versions, missing/extra/duplicate or unsafe paths, changed bytes, invalid media and incompatible legacy audio. All files are validated before copying; each is read and hashed again while copying to guard against external edits. Only a fully restored project is activated.

Unlike the ZIP path, folder processing does not assemble all media into one in-memory archive or impose a 512 MiB total cap. It retains 12,000 files, 8 MiB manuscript/manifest and existing per-media size/decode limits. Restoration still copies media into IndexedDB and needs sufficient browser quota. A storage failure can leave unreferenced content-addressed files, but does not activate the incomplete project. Direct editing from disk, garbage collection, recovery of incomplete backups, cancellation and concurrent-editor conflict handling remain unfinished.

The browser test uses real Origin Private File System handles in place of the operating-system picker, so it exercises file I/O and the editor flow without claiming OS dialog automation. ### User audio and voice authoring — 2026-09-06

The inspector now imports music, sound effects and per-line voice recordings. MP3, Ogg Vorbis/Opus and uncompressed 16-bit PCM WAV are recognized from their bytes and probed for browser decode support and finite duration before one media-storage transaction. The original bytes are retained under SHA-256 paths; imported batches that fail validation do not register partial manuscript entries. Limits are 50 MB / 30 minutes per file, 50 files / 200 MB per batch and 5,000 registry entries. The searchable library renders at most 40 audio controls per page. Used files cannot be removed from the registry until scene/line references are cleared. Physical media garbage collection remains a separate unfinished task.

The local asset worker supports full responses and single byte ranges, so browser media can read metadata and seek. Export and restoration verify content-addressed paths against actual file hashes. User audio bytes are included in standalone ZIPs and rehydrated in a clean browser; legacy fixed-ID audio still requires the installed version's matching bytes. Browser ZIP restoration retains its 512 MB total limit; its file-count limit is now 12,000 to accommodate the image and voice registries together. These are not unlimited-size desktop projects.

The web runtime plays custom music/effects, exposes separate voice volume, pauses voice in menus, stops it when advancing, and waits for voice completion before automatic advance. An existing null-BGM bug was fixed: stopping music now pauses both crossfade slots and clears their tracks. Late playback rejection from an obsolete voice cue cannot mark the next cue failed. Sound-effect template caching is bounded at 32 entries. Native export emits Ren'Py voice statements and resolves user music/effect paths without rewriting the originals.

### Explicit native release baseline selection — 2026-09-06

The editor's **업데이트 기준 빌드** selector now pins a particular completed release instead of always using the latest successful development build. Automatic latest-build selection remains the default. A pin is stored per native release ID in this browser/site, persists across reload, and is captured before bundle preparation. Switching the selector back to automatic removes the pin. A malformed stored preference can be explicitly reset even when no release is available. This preference is not embedded in the manuscript or synchronized between computers.

The loopback-only `/api/native-build/baselines/<releaseId>` endpoint filters the full retained history to completed jobs for that release and provides 50-row pages. Selecting an older page does not change the chosen baseline. ### Native manuscript compatibility review — 2026-09-06

`nativeCompatibility.ts` compares the verified baseline manuscript with a current manuscript and reports high-priority review, ordinary review and informational findings. It detects removed scene IDs, line count changes, inversions among surviving dialogue anchors, choice count/order/logic changes, scene exits, removed/type-changed/default-changed/added flags, actor removal/ordinal/settings changes, stage cues and library metadata. Object key order is ignored. The matcher cannot infer persistent line identity or distinguish every simultaneous rewrite and reorder. It never returns a runtime “compatible”/pass verdict; even no detected changes carries explicit limitations. Counts cover all findings while details retain at most 400, prioritizing high findings; omissions are visible.

The read-only, same-origin `/api/native-build/compatibility` endpoint accepts at most 8MiB of strict UTF-8 JSON and resolves the selected local baseline with the same archive size/SHA/manuscript identity checks as native builds. It performs no SDK execution or file installation. The editor's comparison is a snapshot; changing the manuscript or selected baseline clears it and invalidates pending responses. It can be downloaded separately. Automatic selection is resolved again at build time, and exported asset paths may differ from authoring paths, so the preflight is not a frozen release manifest.

When exporting against a baseline, `release-compatibility.json` is recomputed from the actual rebased export manuscript and included in the native project/package. It records the baseline job/archive hash and both manuscript hashes. Job metadata retains its SHA-256 and severity counts, and the completed-build UI shows counts and the stored report. The `/jobs/<id>/compatibility` download verifies the retained report hash; missing reports on older jobs are not manufactured. High findings do not block an authorized build. They require real save restoration tests rather than being treated as a proof of incompatibility or a successful migration.

Unit tests cover unchanged/key-reordered data, type/default/deletion/addition of state, duplicate dialogue anchors, scene/choice/line changes, actor order, priority retention and omission counts. The separate-server history fixture proves report hash/count persistence and raw report restoration, detects tampering, and rejects malformed UTF-8/JSON and oversized preflight bodies. Its report is a byte fixture, not a playable game. Workspace tests, typechecking and production build pass (`evidence/native-compatibility-tests.log`, `native-compatibility-typecheck-final.log`, `native-compatibility-build.log`).

The self-contained browser/SDK test builds a baseline, deletes a scene, inserts a line, removes a choice and changes/adds flag defaults. It verifies preflight findings and source hashes, clears a stale result after title editing, builds the revised game, opens/downloads the stored report, and compares its hash with job metadata and the packaged ZIP entry. The final run passes on the original 5184 server (`evidence/native-compatibility-e2e-final.log`). Desktop and 390-pixel screenshots are captured in `evidence/native-compatibility/`; report JSON and job IDs are retained there. This tests the comparison/report pipeline, not loading old saves after these destructive changes.
