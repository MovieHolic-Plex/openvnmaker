# grok CLI 이미지 생성·편집 방법론

vnmaker의 모든 생성 이미지는 grok CLI를 통해 만든다. 확인 일자 2026-08-31.
(노션에 붙여넣기용 문서. 원본은 이 파일.)

## 1. 무엇이 있는가

grok CLI(`C:\Users\ubbio\.grok\bin\grok.exe`)에는 두 개의 이미지 툴이 있다.
`grok models`나 시작 가이드의 툴 표에는 **나오지 않는다** — 그것만 보면 없다고 오판한다.

| 표면 | 정체 |
|---|---|
| `image_gen` | 텍스트 → 새 이미지. `prompt`(필수), `aspect_ratio`(`1:1` `16:9` `9:16` `4:3` `3:4` `auto`) |
| `image_edit` | 기존 이미지 + 프롬프트 → 변형. `prompt`(필수), `image`(필수, 파일 경로 또는 `data:image/...;base64,`), `aspect_ratio`(다중 이미지 편집 시에만) |
| `/imagine <설명>` | 대화형 슬래시 커맨드 |
| `/imagine-video <설명>` | 샷 계획 → 소스 이미지 → `image_to_video` |

게이팅: `features.image_gen`(불리언, `~/.grok/config.toml`), `features.image_gen_model_override`,
`features.image_edit_model_override`, `features.video_gen`.
병렬 상한: `tools.media_gen.max_parallel_image_gen_calls`(기본 8) / 환경변수 `GROK_MAX_PARALLEL_IMAGE_GEN_CALLS`.

규약 원본: `~/.grok/bundled/skills/imagine/SKILL.md`.
게임 자산용 특화 스킬: `game-asset-core`, `game-character-consistency`, `game-animation-frames`,
`game-tilesets`, `game-ui-icons` (`~/.grok/bundled/skills/`).

없는 것: `n`/`count` 파라미터(변형은 호출을 여러 번), 텍스트→비디오(비디오는 항상 이미지에서 출발),
지속적인 캐릭터·스타일 메모리.

## 2. 호출 방법 (헤드리스)

`~/.grok/config.toml`에 `permission_mode = "always-approve"`가 이미 있어서 그대로 돌아간다.

```powershell
$p = @'
Use the image_gen tool to create one illustration, then save the generated image file to
<상대경로>.png (create dirs if needed) and print the absolute path plus the file size.

Prompt for image_gen: <2~5문장 산문 프롬프트>

aspect_ratio: 16:9. Do not add any text to the image.
'@
& "C:\Users\ubbio\.grok\bin\grok.exe" -p $p --always-approve
```

에이전트가 `image_gen`을 호출하고 `run_terminal_command`로 목적지에 저장한다.
저장 경로를 프롬프트에 명시하지 않으면 세션 임시 위치에만 남는다.
`-p`는 단일 턴이므로 여러 장은 호출을 나누거나 한 프롬프트에 단계를 순서대로 적는다.

검증된 것: `image_gen` + 파일 저장 (2026-08-31, 1.56MB / 16:9 PNG).
미검증: `image_edit`, 비디오 툴 존재 여부. 비디오는 스킬 문서도 "호출 전에 있는지 확인하라"고 적는다.

## 3. 코드로 만들 것과 생성할 것의 경계

이 규칙이 방법론의 핵심이다. 이미지 모델은 정확한 글자·숫자·구조에서 신뢰할 수 없다.
프롬프트를 정교하게 써도, `image_edit`으로 고쳐도 안 된다.

- **코드로 만든다(HTML+CSS 우선, Python 플로팅보다 낫다)**: 실측치 차트, 라벨 달린 다이어그램, 표,
  실제 문구가 들어간 화면, 그리고 프레임·패널 경계·라벨이 정확해야 하는 다중 패널 레이아웃
  (콘택트 시트, 스토리보드, 만화 그리드).
- **생성한다**: 사진, 일러스트, 캐릭터, 배경, 장식 아트 — 겉모습만 중요한 것.

기획서 PDF에 적용하면: 그림 11개(막대·그룹막대·레인 다이어그램)는 전부 코드 SVG로 유지하고,
표지와 개념 일러스트만 `image_gen`으로 만든다.

## 4. 프롬프트 작성

- 순서: **주체 → 동작/포즈 → 배경 → 스타일 → 구도 → 조명/분위기 → 핵심 디테일**
- 자연스러운 산문 2~5문장. 키워드 태그 나열 금지. 부정 프롬프트 대신 넣을 것을 서술한다.
- 한 프롬프트에 한 장면. 스타일/매체 단어는 항상 넣는다.
- 수량·기하는 숫자로 쓰지 말고 이름 붙일 수 있는 시각적 배치로 표현한다(시계 방향 위치, 파이 조각, 색 마커).
- 사용자가 프롬프트를 줬으면 **그대로** 쓴다.
- `aspect_ratio`를 용도에 맞춘다: `16:9` 배너·표지, `9:16` 세로, `1:1` 아이콘·아바타.
- 편집은 **바뀌는 것만** 서술하고, 유지할 것을 함께 못박는다.

## 5. 일관성은 매 호출마다 만들어야 한다

grok에는 캐릭터·스타일 메모리가 없다. "같은" 대상을 따로 생성하면 항상 드리프트한다.

1. 정본 레퍼런스 1장을 `image_gen`으로 먼저 만든다.
2. 이후 모든 재등장은 그 레퍼런스를 `image` 로 넣은 `image_edit`으로 파생시킨다. 새로 `image_gen` 하지 않는다.
3. 매 프롬프트에 고정 특성과 불변 규칙을 다시 적는다.
4. 결과를 레퍼런스와 대조 검증한다.
5. 한 장면의 여러 각도는 장면 마스터 1장에서 각각 파생시킨다.

다중 패널은 한 장의 생성이 아니라 파이프라인이다: 레퍼런스 → 패널별 개별 생성 → **그리드·보더·라벨은 코드로 조립**.

## 6. VN 자산에 적용 (vnmaker §7)

`game-asset-core`가 요구하는, 사용자가 말하지 않아도 지켜야 할 기본값:

- 캐릭터/소품 스프라이트: 피사체 분리, 키잉 가능한 단색 평면 배경, 깨끗한 실루엣, 바닥 그림자 없음
- 스프라이트 시트: 구분선 없이 균일한 암묵적 셀, 셀마다 피사체 동일 위치 → `width/cols × height/rows`로 크롭됨
- 같은 캐릭터 재요청: 기존 베이스에서 편집 체인. 재생성 금지
- UI 패널/버튼: 9-슬라이스로 확대 견딤, 이미지에 **글자 절대 금지**(게임은 현지화된다), 상태 변형은 기하 동일
- 아이콘: 세트 전체 한 스타일 계약, 균일 패딩, 32px에서 판독 가능

표정 시트는 이 규약대로면 정본 스프라이트 1장 → 표정별 `image_edit` 체인이다.

## 7. 검증 루프

1. 결과를 만든다.
2. **실제 출력을 읽어본다.** 이미지 이해로 되읽어 모든 글자·숫자·라벨·구조를 요구사항과 대조한다.
   겹침·잘림·캔버스 이탈도 본다.
3. 틀렸으면: 이미지 모델이 글자를 뭉갰거나 숫자를 발명했으면 재프롬프트하지 말고 **코드로 다시 만든다**.
   코드 산출물의 겹침은 좌표 손보지 말고 오토레이아웃으로 다시 잡는다. 그 외에는 한 번의 표적 편집.
4. 정확해질 때까지 끝내지 않는다. 정확해질 수 없으면 **틀린 걸 내보내지 말고 사용자에게 말한다.**

검증 규율(`game-asset-core`): 스펙을 다시 읽기 **전에** 이미지가 보여주는 것을 먼저 서술하고 나서 대조한다.
자기 서술에 애매한 말이 섞이면 그것이 곧 실패다. "이 정도면 됐다" 없음.
표적 재시도는 1회, 같은 실패가 반복되면 그건 모델의 prior이므로 합성으로 조립하거나 최선을 남기고 결함을 **명시**한다.
증명하려는 지점당 폐기 2장까지.

## 8. 안전·실패

- 모더레이션 차단: 멈춘다. 재시도·우회 표현 금지. 사용자에게 차단 사실을 말하고 다른 방향을 제안한다.
- 실명 인물: 순수 `image_gen` 금지. 웹 검색으로 신원 확인 후 실제 레퍼런스로 `image_edit`.
  적절한 레퍼런스가 없으면 약한 베이스로 생성하지 말고 업로드를 요청한다.
- 실세계 사실이 걸린 요청: 생성 전에 검색해 확인된 세부를 프롬프트에 넣는다. 기억에 의존하지 않는다.
